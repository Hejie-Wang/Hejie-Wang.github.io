# 如何管理好一个科研仓库

现在AI辅助科研越来越多，在这个浪潮下，一个科研人一天的产出代码量就足以堆积成一个科研仓库。如果没有好的仓库管理，对各个部分代码进行分类。不单是自己很难从这些堆积如山的代码中找到自己想要的东西，更重要的是，这些代码作为知识库在进入agent的时候，其排列组合的方式可能并不是你想要的，这样无疑会降低agent的效率，让一个人头大而苦恼。

## Zen of Research Repository

一个研究的目录下，可能会混杂着实验意图、一次性实验代码、可复用的主要代码和研究结论。扁平化的仓库目录通常命名其为`code`，`idea`，`conclusion`，或者更好的，还有`tools`，`data`，`docs`，`experiments`，`results`这样进一步的分类。但是这样的分类依然有问题，比如你无法从命名中知道某一个在`docs`目录下面的文档是否是过期的思路，或者，你也无法分辨`experiments`目录下的实验哪些是重要的实验结论，哪些是一次性探索完就抛弃的实验。

于是，纵向的命名仓库方式就显得很有必要了，能从其中看到一个实验的生命周期，也能看到一个想法是如何从验证，到实现，进一步改进，最后形成稳定的结果结论；还可以在跨目录精确找到横向目录（文件功能）和纵向关系（实验阶段）的交叉点，也就是一个实验所属的精确坐标。

```text
research-repo/
├── README.md                 # 项目研究目标与当前状态
├── AGENTS.md                 # Agent 使用仓库的规则
├── CODEMAP.md                # 人工维护的核心代码导航
│
├── src/
│   └── project_name/
│       ├── data/             # 稳定的数据处理接口
│       ├── models/           # 可复用模型组件
│       ├── training/         # 训练流程
│       ├── evaluation/       # 统一评测
│       └── utils/
│
├── experiments/
│   ├── index.yaml            # 实验索引，供人和 Agent 检索
│   ├── exp_001_baseline/
│   │   ├── README.md         # 问题、假设、结论、状态
│   │   ├── config.yaml
│   │   ├── run.py
│   │   └── notes.md
│   ├── exp_002_new_loss/
│   └── _archive/             # 已结束、不默认提供给 Agent
│
├── sandbox/                  # AI 生成代码、临时验证、一次性脚本
├── notebooks/                # 快速验证、可视化、分析
├── tests/
├── scripts/                  # 少量通用运维脚本
├── docs/
│   ├── ideas/                # 研究意图、思路、假设
|   ├── findings/             # 沉淀后的研究结论
│   └── _archive/             # 废弃的结果或思路
│
├── configs/                  # 跨实验共享的配置
├── data/                     # 通常只放说明、索引或下载脚本
└── artifacts/                # 日志、权重、图表，一般不提交 Git
```

上述代码仓库可以分为四个模块：核心代码模块、实验模块、文档模块和临时模块。虽然上述的目录架构是针对AI研究领域来做的，但是对其他科研领域一样适用。整体根目录下面，有一个`src`目录，里面是骨干代码和可复用的工具模块；有一个`experiments`目录，里面是实验的生命周期管理，包含了实验的索引和实验的具体实现，每个实验都有一个独立的目录，里面包含了实验的配置、代码、结果和结论，还有实验的状态说明（已废弃会移至`_archive`目录）；有一个`docs`目录，其中存放了研究意图、重要实验结论（废弃文档放在`_archive`目录中）；最后是临时探索工作的内容，包括 AI 临时生成的脚本、`Notebook`、调试代码、日志、权重、图表和中间数据，先允许乱，但乱要有边界。

实验可以调用稳定代码，但稳定代码不应该引用某个实验目录；可复用的探索代码经过整理后，才能从 sandbox 或 experiments “晋升”到 src。这样一来，纵向的思路流动就可以在仓库中被清晰地呈现出来，仓库管理升维带来了效率的提升。

## Rules of Research Repository

框框有了，规则也要有。

1. `src`目录下的代码是稳定的、可复用的，不能随意修改，除非有充分理由。
2. `experiments`每个实验都要回答“为什么存在”，在`README.md`中写明。比如:
```markdown
# EXP-002：验证不确定性加权损失

- 状态：已完成
- 研究问题：不确定性加权是否能提高小样本场景的泛化能力？
- 假设：降低高噪声样本权重可以改善验证集表现。
- 基线：EXP-001
- 核心改动：仅修改损失函数，不改变数据与训练轮数。
- 运行命令：python experiments/exp_002_new_loss/run.py
- 结果：见 artifacts/exp_002/
- 结论：验证集提升有限，暂不合入默认训练流程。
- 后续：检查不同噪声比例下的表现。
```
再通过`.yaml`文件加入机器可读的索引，这样，Agent 可以先根据 status、tags、baseline 和 summary 筛选实验，再读取需要的文件。

3. `AGENTS.md`写明仓库阅读的规则，比如：
```markdown
# 仓库使用规则

## 阅读顺序
1. README.md：了解研究目标。
2. CODEMAP.md：定位核心模块。
3. experiments/index.yaml：查找相关实验。
4. 只在必要时读取具体源码。

## 可信范围
- src/：稳定、可复用代码。
- experiments/：具体实验，不代表通用实现。
- sandbox/：未验证代码，禁止直接复用。
- experiments/_archive/：历史实验，默认忽略。

## 修改规则
- 不在实验目录复制整套公共代码。
- 修改 src/ 中公共接口时，必须补充或更新测试。
- 新实验必须包含 README、配置、入口和状态。
- AI 生成代码先放入 sandbox/，验证后再迁移。

## 完成标准
- 入口可以运行或明确说明缺失依赖。
- 记录配置、代码版本和结果位置。
- 说明本次修改影响了哪些实验。
```

4. 同样的，在`CODEMAP.md`中写明核心代码的功能和调用关系，只维护核心代码内容。
5. 关于测试验证代码，首先在`notebooks`或者`sandbox`中进行快速验证，然后进入`experiments`目录进行实验，之后需要重构代码，删除重复加载数据代码等，，最后才可以进入`src`目录，成为人可以稳定阅读和复用的代码。
6. 最后，实验、数据与结果不要混为一谈。分别管理：

- Git：源码、配置、实验说明、小型测试结果；
- DVC、Git LFS 或对象存储：数据集、权重、大型结果；
- 实验索引：记录实验与代码版本、数据版本、结果路径的关系；
- 结论文档：记录“得到了什么”，而不只是“运行过什么”。

```text
实验 ID + Git commit + 配置 + 数据版本 + 随机种子 + 运行命令 + 结果路径
```
让实验结果一目了然

## Suggested Practices

1. 采用低成本维护节奏
不需要每天设计复杂架构，只要坚持三个动作：

每次实验结束：更新状态与一句结论。
每周一次：清理 sandbox，归档已结束实验，合并重复代码。
删除和归档不是损失。对 Agent 来说，过时代码往往比没有代码更有害，因为它会参与检索并干扰判断。

2. 用几个任务检验仓库是否真的管用，定期让 Agent 在不了解背景的情况下完成这些任务：

“哪个实验支持当前论文中的核心结论？”
“复现当前最佳基线需要运行什么？”
“修改损失函数应该改哪个文件？”
“哪些实验已经证明某方案无效？”
“新增一个对照实验，不得修改公共基线。”

如果 Agent 仍然大量读取废弃脚本、找错入口或复制公共代码，问题通常不在模型能力，而在仓库没有清楚表达可信边界和实验关系。

## Conclusion

组织规模逐渐变大，就会遇到这样的问题。原有的小作坊下猛料的突击式工作办法不适合大规模科研进展。并且在这个大规模AI实现代码阶段，反而是有害的，思路不能流畅地流动。在AI时代，《论持久战》对于科研的含金量还在上升。亡国论认为AI就要取代科研人员，速胜论认为“老登，时代变了，同时多线程工作不是梦想”。持久战的科研，就需要像这样一个一个科研仓库的经验积累过去，和AI共生，达到思路和实践的平衡。
